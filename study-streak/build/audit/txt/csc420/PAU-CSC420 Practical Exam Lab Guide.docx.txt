Lab 1.1 Atomicity, the success path
Ada drops CS-347: remove her enrolment and take back the credits, as one unit.
BEGIN;DELETE FROM takes WHERE id = 1 AND coursecode = 'CS-347';UPDATE student SET tot_cred = tot_cred - (SELECT credits FROM course WHERE coursecode = 'CS-347') WHERE id = 1;COMMIT;SELECT tot_cred FROM student WHERE id = 1;        -- 7SELECT count(*) FROM takes WHERE id = 1;          -- 0
TESTED. Both changes happened. That is atomicity working normally.
Lab 1.2 Atomicity, the failure path (a typo in step two)
Now Bola drops PH-101, but the second statement has a typo (courses instead of course).
BEGIN;DELETE FROM takes WHERE id = 2 AND coursecode = 'PH-101';UPDATE student SET tot_cred = tot_cred - (SELECT credits FROM courses WHERE coursecode = 'PH-101') WHERE id = 2;COMMIT;SELECT count(*) FROM takes WHERE id = 2;          -- 1 (the DELETE was undone)
TESTED. The first line reports DELETE 1, the second fails with relation "courses" does not exist, and the COMMIT line prints ROLLBACK, not COMMIT. The enrolment is still there.
What to observe and say in the exam: after an error inside BEGIN ... COMMIT the transaction is dead. Postgres rolls everything back, even the statement that printed success. A later command in the same block would say current transaction is aborted, commands ignored until end of transaction block (ADDITIONAL CONTEXT).

Lab 1.5 ROLLBACK by hand
BEGIN;UPDATE student SET tot_cred = 99 WHERE id = 1;SELECT tot_cred FROM student WHERE id = 1;   -- 99 (you see your own change)ROLLBACK;SELECT tot_cred FROM student WHERE id = 1;   -- 7 (back to the prior state)
TESTED. ROLLBACK is the command that gives the aborted state its meaning: the database is restored to its prior state.
Lab 1.6 Durability (know it, you cannot demo it safely)
Durability means committed changes survive a crash because every change is written to the write-ahead log (WAL) before the data files. After a crash, Postgres replays the log on restart. Do not try to crash your server; just be able to say it.

How to read any plan (do this every time)
Find the scan node: Seq Scan, Index Scan, Bitmap Heap Scan (with a Bitmap Index Scan under it), or Index Only Scan.
Read the condition line: Filter (checked row by row after reading) or Index Cond (used to search the index).
Read Rows Removed by Filter. A huge number with one row returned screams "add an index".
For Index Only Scan, check Heap Fetches: 0.
Compare Execution Time before and after (only EXPLAIN ANALYZE gives it).
Plain EXPLAIN shows the plan without running the query. EXPLAIN ANALYZE runs it (so on INSERT, UPDATE or DELETE it really changes data; I confirmed it does, so wrap those in BEGIN ... ROLLBACK).
Lab 2.1 Baseline: no index
EXPLAIN ANALYZE SELECT * FROM people WHERE name = 'Leonardo DiCaprio';
TESTED (trimmed): Parallel Seq Scan on people, Filter: (name = 'Leonardo DiCaprio'::text), Rows Removed by Filter: 200000 per worker, Execution Time: 42.8 ms. Your slide showed 430,491 rows removed and 85.97 ms on the real data. Same shape, bigger table.
Lab 2.2 Single-column B-tree
CREATE INDEX idx_name ON people (name);EXPLAIN ANALYZE SELECT * FROM people WHERE name = 'Leonardo DiCaprio';
TESTED: Index Scan using idx_name, Index Cond: (name = ...), Execution Time: 0.054 ms. The full scan became a lookup, roughly 800 times faster here.
Lab 2.3 Add a hash index on the same column
CREATE INDEX idx_name_hash ON people USING hash (name);EXPLAIN ANALYZE SELECT * FROM people WHERE name = 'Leonardo DiCaprio';
TESTED: the plan now says Index Scan using idx_name_hash. With two usable indexes, the planner chose the hash for an equality query, as slide 40 says.
Now prove hash is equality-only. Drop it and try a range:
DROP INDEX idx_name_hash;EXPLAIN SELECT * FROM people WHERE name > 'Person 99990' AND name < 'Person 99992';
TESTED: the B-tree is used (Index Scan using idx_name). A hash index on a range query is useless: with only a hash index on birth, the query WHERE birth > 2000 stayed a Seq Scan.
Lab 2.4 Covering index (INCLUDE) and Index Only Scan
Baseline, then a plain index, then the covering index:
EXPLAIN ANALYZE SELECT movie_id, votes FROM ratings WHERE rating > 9.5;   -- Seq ScanCREATE INDEX idx_rating ON ratings (rating);EXPLAIN ANALYZE SELECT movie_id, votes FROM ratings WHERE rating > 9.5;   -- Bitmap Heap ScanDROP INDEX idx_rating;CREATE INDEX idx_rating_incl ON ratings (rating) INCLUDE (movie_id, votes);VACUUM ratings;EXPLAIN ANALYZE SELECT movie_id, votes FROM ratings WHERE rating > 9.5;   -- Index Only Scan
TESTED: Seq Scan 39 ms (284,902 rows removed), plain index Bitmap Heap Scan 7.5 ms, covering index Index Only Scan with Heap Fetches: 0 at 3.3 ms. The slide's before and after (13.557 ms to 2.714 ms) shows the same story.
Two practical notes: (1) The planner may pick a bitmap scan for the plain index even though the slides' version shows a Seq Scan; the plan depends on how selective the condition is. (2) The VACUUM matters: an Index Only Scan relies on the table's visibility map, so after bulk loads run VACUUM or you may see Heap Fetches above 0 (ADDITIONAL CONTEXT).
One sentence for the exam: a covering index stores the extra columns with INCLUDE, so the query is answered from the index alone and the table is never read.
Lab 2.5 Partial index
CREATE INDEX idx_ratings_blockbuster ON ratings (votes) WHERE votes > 199000;EXPLAIN SELECT * FROM ratings WHERE votes > 199500;   -- uses the partial indexEXPLAIN SELECT * FROM ratings WHERE votes > 150000;   -- Seq Scan

Lab 2.6 Functional (expression) index
EXPLAIN SELECT * FROM people WHERE lower(name) = 'person 5';   -- Seq Scan (index on name is no help)CREATE INDEX idx_lower_name ON people (lower(name));EXPLAIN SELECT * FROM people WHERE lower(name) = 'person 5';   -- now uses idx_lower_name
TESTED. The query must use the same expression as the index. An index on name does not help a query on lower(name).
Lab 2.7 Composite index and the leading column
CREATE INDEX idx_stars_comp ON stars (movie_id, person_id);EXPLAIN SELECT * FROM stars WHERE movie_id = 100;                    -- uses the indexEXPLAIN SELECT * FROM stars WHERE movie_id = 100 AND person_id = 5;  -- Index Only ScanEXPLAIN SELECT * FROM stars WHERE person_id = 5;                     -- Seq Scan
TESTED. The index helps when the query filters on the leading column (movie_id). Filtering only on the second column (person_id) did not use it. (The slides do not state this rule; it is ADDITIONAL CONTEXT, but you just saw it happen.)
Lab 2.8 Bitmap scans
CREATE INDEX idx_movies_year ON movies (year);EXPLAIN ANALYZE SELECT * FROM movies WHERE year BETWEEN 1990 AND 1992;EXPLAIN SELECT * FROM movies WHERE year = 1990 OR year = 2000;EXPLAIN SELECT * FROM movies WHERE year > 1951;
TESTED:
The BETWEEN query gives Bitmap Heap Scan on movies, Recheck Cond: ..., Heap Blocks: exact=1911, with a Bitmap Index Scan on idx_movies_year underneath: the two-phase plan for a medium-selectivity query.
The OR query shows a BitmapOr joining two Bitmap Index Scans (bitmaps combined before touching the table).
year > 1951 matches almost every row, so Postgres ignores the index and uses a Seq Scan. When most of the table is needed, reading it straight through is cheaper.
Selectivity ladder: very few rows = Index Scan; a medium slice = Bitmap Index plus Bitmap Heap Scan; the index holds everything = Index Only Scan; most of the table or no usable index = Seq Scan.
Lab 2.9 LIKE prefix and the question mark on slide 38
EXPLAIN SELECT * FROM people WHERE name LIKE 'Person 1234%';   -- Seq Scan with the default B-treeCREATE INDEX idx_name_tpo ON people (name text_pattern_ops);EXPLAIN SELECT * FROM people WHERE name LIKE 'Person 1234%';   -- Index ScanEXPLAIN SELECT * FROM people WHERE name LIKE '%1234';           -- Seq Scan (unanchored)
TESTED on my server (default locale, not the C locale). This resolves slide 38's "?": a B-tree can serve a prefix pattern only when the index uses text_pattern_ops (or the database uses the C locale), and never a pattern starting with %. Lab 2.10 Over-indexing: see the cost
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS sizeFROM pg_stat_user_indexes WHERE relname = 'people';

-- FUNCTION: computes and returns a value; use it inside SELECTCREATE OR REPLACE FUNCTION fn_name(p_arg INT) RETURNS NUMERICLANGUAGE plpgsql AS $$DECLARE v_x NUMERIC;BEGIN  SELECT ... INTO v_x FROM ... WHERE ... = p_arg;  RETURN v_x;END;$$;-- PROCEDURE: does a multi-step job; no return value; run it with CALLCREATE OR REPLACE PROCEDURE sp_name(p_arg INT)LANGUAGE plpgsql AS $$BEGIN  UPDATE ... ;  INSERT ... ;END;$$;-- TRIGGER: two parts. 1) the trigger function  2) the triggerCREATE OR REPLACE FUNCTION trg_fn_name() RETURNS TRIGGERLANGUAGE plpgsql AS $$BEGIN  NEW.col := ... ;      -- BEFORE only  RETURN NEW;           -- BEFORE: return NEW (or NULL to skip the row)END;$$;CREATE TRIGGER trg_name BEFORE INSERT OR UPDATE ON some_tableFOR EACH ROW EXECUTE FUNCTION trg_fn_name();
Checklist when you write one: language plpgsql; the $$ quotes opened and closed; BEGIN ... END; with a semicolon after END; a RETURN in every function path; RETURN NEW in a BEFORE row trigger; the trigger function RETURNS TRIGGER. Naming from the lecture: fn_ for functions, sp_ for procedures, trg_fn_ for trigger functions, trg_ for triggers.

Lab 4.4 AFTER trigger: record, do not change
CREATE TABLE order_log (log_id serial PRIMARY KEY, order_id text, action text, logged_at timestamptz DEFAULT now());CREATE FUNCTION trg_fn_order_log() RETURNS TRIGGER LANGUAGE plpgsql AS $$BEGIN  INSERT INTO order_log(order_id, action) VALUES (NEW.order_id, TG_OP);  RETURN NULL;     -- ignored in an AFTER triggerEND;$$;CREATE TRIGGER trg_order_log AFTER INSERT OR UPDATE ON ordersFOR EACH ROW EXECUTE FUNCTION trg_fn_order_log();

Lab 4.5 BEFORE trigger: veto or skip a row
CREATE FUNCTION trg_fn_price_check() RETURNS TRIGGER LANGUAGE plpgsql AS $$BEGIN  IF NEW.price <= 0 THEN    RAISE EXCEPTION 'Price must be positive, got %', NEW.price;  END IF;  RETURN NEW;END;$$;CREATE TRIGGER trg_price_check BEFORE INSERT OR UPDATE ON variationsFOR EACH ROW EXECUTE FUNCTION trg_fn_price_check();UPDATE variations SET price = -5 WHERE product_id = 1 AND variation_no = 1;
TESTED: ERROR: Price must be positive, got -5.00, and the price is unchanged. Returning NULL from a BEFORE row trigger instead skips that row silently (I tested this too: the INSERT reported INSERT 0 0). Use RAISE EXCEPTION when you want a loud failure, NULL when you want to quietly drop the row.
Constraint first: a rule about one row's own values, like price above zero, is better as CHECK (price > 0). The trigger above is only the practice pattern (slide 34: prefer constraints).

Practical Cheat Sheet
Transactions
BEGIN;  ...statements...  COMMIT;    -- all permanentBEGIN;  ...statements...  ROLLBACK;  -- all undone
Error in the block = whole block fails. States: active, partially committed, committed, failed, aborted. Only partially committed reaches committed; only failed reaches aborted.
Indexes and plans
EXPLAIN SELECT ...;                       -- plan onlyEXPLAIN ANALYZE SELECT ...;               -- runs it, real timingsCREATE INDEX i ON t (col);                -- B-tree (default)CREATE INDEX i ON t USING hash (col);     -- equality onlyCREATE INDEX i ON t (a, b);               -- composite (leading column matters)CREATE INDEX i ON t (a) INCLUDE (b, c);   -- covering, Index Only ScanCREATE INDEX i ON t (a) WHERE cond;       -- partialCREATE INDEX i ON t (lower(a));           -- functionalCREATE INDEX i ON t USING GIN (col);      -- arrays, JSONB, full-text
