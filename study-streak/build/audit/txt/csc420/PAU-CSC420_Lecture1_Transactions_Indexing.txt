What Is a Transaction?
A transaction is a unit of program execution that 
accesses — and possibly updates — various data 
items in the database.
Example: transferring funds between two 
accounts, or registering a student for a course.
To preserve the integrity of the data, the database 
system must guarantee four properties — known 
by the acronym ACID: Atomicity, Consistency, 
Isolation, and Durability

--- page 6 ---
ACID: Atomicity & Consistency
Atomicity. Either all operations of the transaction 
are properly reflected in the database, or none 
are.
Consistency. Executing a transaction in isolation 
(with no other transaction running concurrently) 
preserves the consistency of the database.
▪ If a transaction violates a consistency constraint 
partway through, the whole transaction is rolled back; 
that is, nothing is left half-done.
6
Dr. Stephen A. Adubi
--- page 7 ---
ACID: Isolation & Durability
Isolation. Although multiple transactions may 
execute concurrently, each must be unaware of the 
others — intermediate results stay hidden from 
concurrently executing transactions.
Durability. After a transaction completes successfully, 
its changes persist even if the system subsequently 
fails.
PostgreSQL enforces isolation with its concurrency-
control mechanisms, and durability with write-ahead
logging (WAL).

Transaction States
Active — the initial state; the transaction stays here while it 
is executing.
Partially committed — after the final statement has 
executed.
Failed — after the system discovers that normal execution 
can no longer proceed.
Aborted — after the transaction has been rolled back and 
the database restored to its prior state. Two options follow:
▪ Restart the transaction — only if there was no internal logical 
error.
▪ Kill the transaction.
Committed — after successful completion.

Durability & Write
-
Ahead Logging
Durability guarantees that once a transaction 
commits, its changes survive even a subsequent 
crash.
PostgreSQL implements durability with write-ahead 
logging (WAL): every change is recorded in the log 
before it is applied to the actual data files.
If Postgres crashes immediately after a COMMIT, WAL 
replay on restart guarantees the committed changes 
are recovered.
This is why COMMIT is the point of no return — once 
it returns successfully, the data is safe.

Why Are Indexes So Popular?
A sequential scan of a table with N rows has a complexity of 
O(N) — Postgres may inspect every row to find a match.
An index is a data structure that stores indexed values in 
sorted order for faster access.
▪ Postgres's default, general-purpose index type is the B-tree (a 
B+- tree variation).
Searching a B-tree index costs O(logᵇN), where b is the 
branching factor — far fewer lookups than a full scan, and 
the gap widens as the table grows.
▪ Example, branching factor 10: 100 rows → 2 lookups; 1,000 
rows → 3; 1,000,000 rows → 6; 1,000,000,000 rows → 9.

B
+
-
Tree Index Files: Advantages & 
Trade
-
offs
Advantage: a B+-tree index file automatically 
reorganises itself with small, local changes as rows 
are inserted and deleted.
▪  Reorganising the entire file is not required to maintain 
performance.
(Minor) disadvantage: extra insertion/deletion 
overhead, plus some storage overhead.
In practice, the advantages of B+-trees far outweigh 
the disadvantages — which is why they are used so 
extensively, and why PostgreSQL uses them as its 
default index.

Tree Node Structure
Each node holds up to 𝑛 − 1 keys and 𝑛 pointers:
▪ The various 𝐾𝑖 values represent the search-key values 
▪ 𝑃𝑖 are pointers to children (for non-leaf nodes) or pointers 
to records or buckets of records (for leaf nodes).
The search keys in a node are ordered. 
  𝐾1 < 𝐾2 < 𝐾3 < . . . < 𝐾𝑛−1
▪ Initially assume no duplicate keys, address duplicates later.

Leaf Nodes in B
+
-
Trees
A leaf node can hold up to 𝑛 − 1 values (n = the order 
of the tree).
For each key 𝐾𝑖 in a leaf, pointer Pᵢ points either 
directly to the record with that key, or to a bucket of 
pointers when duplicate keys exist.
Leaf nodes are chained together left-to-right, so a 
range query can walk the leaves in sorted order 
without climbing back up the tree.
The last pointer in a leaf, 𝑃𝑛, links to the next leaf 
node in sequence.

Available Index Types in PostgreSQL
Postgres has several index access methods, each suited to 
different kinds of queries:
▪ B-tree — the default; equality and range queries, sorting.
▪ Hash — equality (=) lookups only.
▪ GiST — generalised search tree; geometric types, ranges, nearest-
neighbour search.
▪ SP-GiST — space-partitioned trees; non-balanced data such as quad-
trees and tries.
▪ GIN — generalised inverted index; full-text search, arrays, JSONB 
containment.
▪ BRIN — block range index; very large, naturally-ordered tables.
By default, CREATE INDEX builds a B-tree, which fits the 
majority of situations.

Categorizing Indexes: What vs. How
What we index — the scope or purpose: single-
column, composite, covering, partial, or 
functional/expression. We always make this 
choice.
How we index — the underlying data structure: 
B-tree, Hash, GIN, GiST, SP-GiST, or BRIN. This 
choice is optional — Postgres defaults to B-tree.
▪ CREATE INDEX idx ON t(col);  -- What: single-column · How: B-
tree (default)
▪ CREATE INDEX idx ON t USING GIN (col);  -- What: single-column 
· How: GIN

The EXPLAIN Statement
EXPLAIN shows the execution plan Postgres would use for a 
query, without running it.
EXPLAIN (ANALYZE, …) actually runs the query and reports 
real timings alongside the plan.
Seq Scan — a full, sequential scan of the table.
Index Scan — Postgres walks an index, then fetches 
matching rows from the table.
Bitmap Index / Heap Scan — a two-phase scan for 
medium-selectivity queries (more in the Bitmap Indexes 
section).
Index Only Scan — the index alone has everything the 
query needs; the table is never touched (Heap Fetches: 0).

Hash Index
Hash indexes in Postgres work similarly to hash tables 
or hash maps found in most programming languages.
The index computes a hash for the column value and 
uses it to map the value to a specific bucket.
▪ The algorithmic complexity of hash calculations and 
lookups is O(1), or constant time.
Hash indexes can only be used with the equality (=) 
operator.
▪ Range queries cannot take advantage of hash indexes and 
must use B-tree indexes instead

Practical 4: Covering Index
A covering index is an index that stores additional 
columns from the table, enabling the database to 
retrieve column values directly from the index 
without accessing the table rows.
The additional columns are added to the index 
using the INCLUDE clause:
CREATE INDEX idx_rating_incl ON ratings (rating)
INCLUDE (movie_id, votes);

Bitmap Indexes: The Concept
A bitmap scan is not a separate index type in 
Postgres — it's an access method Postgres chooses 
when scanning an existing B-tree, hash, or other 
index for a moderately selective query.
The idea, in general: for each distinct value, a bitmap 
of one bit per table row marks whether that row 
matches.
▪ 1 = the row matches the condition; 0 = it does not.
Bitmaps for several conditions can be combined with 
bitwise AND / OR before ever touching the table — 
efficient when a plain index scan would otherwise 
revisit the table too many times.
48
Dr. Stephen A. Adubi

How Postgres Executes a Bitmap Scan
Bitmap Index Scan — walks the index and builds an in-memory 
bitmap of every matching row, instead of fetching rows one at a 
time.
Bitmap Heap Scan — visits the table pages named in the bitmap 
and reads the actual rows, in physical (not index) order.
The Heap Blocks line in the plan tells you how precise the 
bitmap was:
▪ exact=N — N pages visited, with exact row locations known.
▪ lossy=N — N pages visited, but Postgres must recheck every row on 
the page, because the bitmap only tracked the page, not the row.
This two-phase approach reduces random table lookups 
compared to fetching one row per index match.

Choosing the Right Index Type
Equality only, few distinct values → Hash (or a 
plain B-tree, which also does equality well).
Range queries, sorting, general purpose → B-tree 
— Postgres's default for good reason.
Several columns filtered together → Composite 
index, most selective / most frequently-filtered 
column leading.
Query needs the indexed columns plus a few 
extras → Covering index (INCLUDE).

Choosing the Right Index Type
Only a small, well-defined slice of the table is 
queried often → Partial index.
Searching on a transformed value → Functional / 
expression index.
Full-text search, arrays, JSONB containment → 
GIN.
Huge, naturally ordered tables (timestamps, 
sequential IDs) → BRIN.

Over
-
Indexing: A Word of Caution
Every index Postgres maintains adds write cost: each 
INSERT, UPDATE, or DELETE must keep every affected 
index consistent, inside the same transaction.
More indexes also mean more work for the query 
planner while it decides which one to use.
Not every query needs to be blazing fast — weigh 
each candidate index against the query's actual 
latency requirements before creating it.
Rule of thumb: index for the queries you actually run, 
and periodically review pg_stat_user_indexes for 
indexes that are never used.

Wrap
-
Up: Key Takeaways
A transaction is a unit of work that Postgres guarantees is 
Atomic, Consistent, Isolated, and Durable (ACID) — all four, or 
the transaction rolls back entirely.
Transaction states — Active, Partially Committed, Failed, 
Aborted, Committed — describe exactly what stage of that 
guarantee a transaction is in.
Indexes trade write cost and storage for dramatically faster 
reads: O(logᵇ N) instead of O(N) for a well-chosen index.
Postgres offers a type for nearly every access pattern — B-tree, 
Hash, composite, covering, partial, functional, GIN, and more — 
and EXPLAIN is how you decide which one, if any, a query 
actually needs.
The imdb practicals showed each of these on a single, realistic 
dataset — keep experimenting with your own queries.
