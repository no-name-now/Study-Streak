Why Complex Types?
In Database Management I, every column held a 
single, atomic value (First Normal Form).
Real data is not always that tidy:
▪ A customer may have zero, one or many phone numbers;
▪ A phone has RAM and storage, a shirt has sizes, an eBook 
has a file size.
PostgreSQL offers complex types that let one column 
hold structured data:
▪ Arrays — a list of values of the same type, e.g. TEXT[].
▪ JSON/JSONB — semi-structured documents of keys, values 
and arrays.
Dr. Stephen A. Adubi

Dos and Don’ts
Consider complex types when data is:
▪ static or rarely updated — e.g. product specs, customer 
preferences;
▪ sparse — many optional keys that are mostly absent;
▪ flexible — its shape differs from row to row.
Prefer ordinary columns and tables when data is 
updated often, joined, aggregated or filtered 
heavily.
Best practice is a hybrid approach: a relational core 
(keys, constraints) plus complex types where they fit.
▪ Caution: foreign keys cannot point into an array or a JSON 
document.

Fewer Tables: What the Complex 
Columns Replace
A fully traditional design of the same business 
rules needs more tables; ours needs seven.
For example:
▪ products.tags and users.favourite_tags (TEXT[]) 
replace two junction tables.
▪ users.mobiles (TEXT[]) replaces a user_mobiles table.
▪ orders.items (JSONB) replaces an order_items table.
▪ Each item stores product_id, variation_no, quantity and the 
unit_price at the time of ordering.

Arrays in PostgreSQL
A column can be an array of any built-in or user-
defined type: TEXT[], INT[], NUMERIC[], …
Array values can be written in two ways:
▪ As a string literal: '{+2348031234567,+2349051234567}'
▪ With the ARRAY constructor: ARRAY['ebook', 'software']
Elements are numbered from 1, not 0.
An empty array '{}' is not the same as NULL — our 
schema uses NOT NULL DEFAULT '{}'.
All elements of an array must have the same type.

Subscripts
Show each customer's main (first) mobile number 
and how many numbers they have.
Halima has no mobiles, so mobiles[1] returns 
NULL and cardinality returns 0.
SELECT first_name, mobiles[1] AS main_mobile,
cardinality(mobiles) AS num_mobiles
FROM users
ORDER BY user_id;

Searching Arrays with 
ANY
Which products are tagged as bestsellers?
The expression value = ANY(array) is true 
when the value matches any element of the array.
SELECT name, tags
FROM products
WHERE 'bestseller' = ANY (tags);

Containment (@>) & 
Overlap (&&)
@> — the left array contains every element of the 
right array.
&& — the two arrays share at least one element.
Find home appliances that save energy, then users 
who like eBooks or smartphones.
SELECT name, tags FROM products
WHERE tags @> ARRAY['home appliance', 'energy saver'];
SELECT first_name, favourite_tags FROM users
WHERE favourite_tags && ARRAY['ebook', 'smartphone'];

Arrays to Rows: unnest
The unnest function turns each array element into 
its own row, so arrays can be grouped and 
counted like normal data.
Which tags are used by the most products?
SELECT tag, count(*) AS num_products
FROM products, unnest(tags) AS tag
GROUP BY tag
ORDER BY num_products DESC;

Updating Arrays
The array_append function adds an element to the end of 
an array.
A subscript replaces one element in place.
User 3 registers her first mobile; User 2 changes his main 
number.
UPDATE users
SET mobiles = array_append(mobiles, '+2348091112223')
WHERE user_id = 3;
UPDATE users SET mobiles[1] = '+2348039998887'
WHERE user_id = 2;

Removing an Element: 
array_remove
The array_remove function deletes every 
occurrence of a value from an array.
Kemi no longer wants 'sale' among her favourite 
tags.
UPDATE users
SET favourite_tags =
array_remove(favourite_tags, 'sale')
WHERE user_id = 11;

Deleting Rows with 
Array Conditions
Remove tags that no product and no user are using.
Arrays cannot hold foreign keys, so ANY is used to 
look inside them.
Two tags are deleted: 'sale' and 'organic'.
DELETE FROM tags t
WHERE NOT EXISTS (SELECT 1 FROM products p
        WHERE t.tag_name = ANY (p.tags))
  AND NOT EXISTS (SELECT 1 FROM users u
        WHERE t.tag_name = ANY (u.favourite_tags));

JSON vs JSONB
JSON stores the original text exactly as written.
▪ Fast to store, but the text must be parsed again every 
time a field is read.
JSONB stores a parsed binary form.
▪ Whitespace is removed, duplicate keys keep only the 
last value, and keys may be reordered.
▪ Faster to query, supports GIN indexes and has more 
operators (e.g. ?, @>).
Rule of thumb: use jsonb unless you must keep 
the original text exactly.

Extracting Fields from 
JSONB
The -> operator returns the field as jsonb (strings 
keep their double quotes).
The ->> operator returns the field as text, ready for 
comparisons and further processing.
Variations without a shipping_class return NULL.
SELECT product_id, variation_no,
  type_details -> 'shipping_class' AS as_json,
  type_details ->> 'shipping_class' AS as_text
FROM variations WHERE product_type = 'physical';

Practical 11

Filtering & Casting 
JSON Values
The ->> operator always returns text, so cast it 
before comparing numbers.
Which variations weigh more than 5 kg?
SELECT p.name, v.variation_no,
  (v.type_details ->> 'weight_kg')::numeric AS weight_kg
FROM variations v
JOIN products p USING (product_id)
WHERE (v.type_details ->> 'weight_kg')::numeric > 5;

Chaining Operators 
into JSON Arrays
The -> operator also accepts an array position 
(starting at 0, unlike SQL arrays).
Chain -> and ->> to reach a value inside the first 
item of each of Adaeze's orders.
SELECT order_id,
  items -> 0 ->> 'product_id' AS first_product,
  items -> 0 ->> 'unit_price' AS first_price
FROM orders WHERE user_id = 1;

Key Exists (?) & 
Containment (@>)
? — Does the document have this top-level key?
@> — Does the document contain this JSON 
fragment?
Find variations that issue licence keys, then variations 
shipped as fragile.
SELECT product_id, variation_no FROM variations
WHERE type_details ? 'licence_key_template';
SELECT product_id, variation_no FROM variations
WHERE type_details @> '{"shipping_class": "fragile"}';

JSON Arrays to Rows: 
jsonb_array_elements
The jsonb_array_elements function expands a JSON 
array into one row per element — the JSON version 
of unnest.
List every item in Adaeze's orders.
SELECT o.order_id,
  item ->> 'product_id' AS product_id,
  item ->> 'variation_no' AS variation_no,
  (item ->> 'quantity')::int AS quantity
FROM orders o, jsonb_array_elements(o.items) AS item
WHERE o.user_id = 1;
Dr. Stephen A. Adubi

Practical 15 
—
 
Joining JSON Items to 
Tables
Once expanded, JSON items join like normal rows.
Which five products have sold the most units?
SELECT p.name, sum((item ->> 'quantity')::int) AS units_sold
FROM orders o, jsonb_array_elements(o.items) AS item
JOIN products p
  ON p.product_id = (item ->> 'product_id')::int
GROUP BY p.name
ORDER BY units_sold DESC
LIMIT 5;

Updating a Value: 
jsonb_set
jsonb_set(document, path, new_value) returns a 
copy of the document with one value changed.
If the key is missing, it is added (the optional 4th 
argument defaults to true).
The new value must be valid JSON, so a string needs 
double quotes.
UPDATE variations
SET type_details = jsonb_set(type_details,
    '{shipping_class}', '"standard"')
WHERE product_id = 16 AND variation_no = 1;

Updating Inside a JSON 
Array
A path can include an array position: '{1,quantity}' 
is the quantity of the second item.
Kemi now wants three tins of milk, so the total 
must rise by 950 in the same statement.
UPDATE orders
SET items = jsonb_set(items, '{1,quantity}', '3'),
    total_amount = total_amount + 950.00
WHERE order_id = '20261001093000_11';

Removing Keys from 
JSONB
The expression jsonb-'key' removes a top-level 
key.
The expression jsonb #- '{path}' removes a 
value at a nested path; e.g. items #- '{0}' drops the 
first item.
Remove the shipping class we added to the Peak 
milk.
UPDATE variations
SET type_details = type_details - 'shipping_class'
WHERE product_id = 16 AND variation_no = 1;

GIN Indexes for Arrays & 
JSONB
GIN indexes (Lecture 1) speed up @> and && on 
arrays, and ? and @> on JSONB.
CREATE INDEX idx_products_tags
  ON products USING GIN (tags);
CREATE INDEX idx_variations_details
  ON variations USING GIN (type_details);

Choosing the Right Type
A simple list of values of one type → an array (e.g. 
mobiles, tags).
Structured data whose shape varies → JSONB (e.g. 
variation details).
Data you must keep exactly as received → JSON.
Data that is updated often, joined or must be 
enforced by foreign keys → a separate table (e.g. 
variations, with its stock levels).
Searching inside arrays or JSONB on large tables → a 
GIN index.

Wrap
-
Up: Key Takeaways
Complex types let one column hold a list (array) or a 
document (JSON/JSONB), reducing the number of 
tables.
Arrays: declare with [], index from 1, search with ANY , 
@> and &&, expand with unnest, and change with 
array_append, array_remove or subscripts.
JSONB is the default choice for JSON: extract with -> 
and ->>, search with ? and @>, expand arrays with 
jsonb_array_elements.
jsonb_set, - and #- change parts of a document 
without rewriting it in the application.
