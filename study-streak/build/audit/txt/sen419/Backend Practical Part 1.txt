The bookmark rules stay the same: max 10 per chapter, notes up to 80 characters, sorted by
timestamp, tap to seek, delete. The difference is that the data now lives on a server, syncs
across devices, and updates live.
What is Convex? A backend platform with a database, server functions, and real-time sync
built in. You write TypeScript functions on the server, call them from React, and the UI
updates automatically whenever the underlying data changes. No REST endpoints, no
manual cache invalidation, no websocket code.
Convex vs. Zustand, in one line: Zustand holds client state (is the audio playing, which
panel is open). Convex holds server state (the library, progress, bookmarks). Use both. Don't
put server data in Zustand.

Books: read the catalog
v.id('books') is a typed relation. A bookmark can only point at a real book, and
TypeScript knows which table the ID belongs to. Use it instead of v.string() for any
reference between tables.
Chapters are embedded, not a fourth table. They're small, they never change per
user, and you always read them with the book. Make a separate table only when the
data grows unbounded, is queried on its own, or changes independently. Splitting
everything into tables is a habit from SQL that Convex doesn't need.
The bookmark index returns results already sorted by time. That's your "auto-
sorted by timestamp" requirement, with no sorting code and no full table scans.

Exercises
Authentication: Convex Auth, Clerk, or any OIDC provider. Without it,
getUserIdentity() returns null and the user-scoped functions above won't work.
Pagination: usePaginatedQuery for long lists such as a big library.
File uploads: the schema already references _storage for covers. Add an upload flow
using ctx.storage.generateUploadUrl().
Scheduled functions and crons: run cleanup jobs or "continue listening" reminders on
a schedule.
Convex components: drop-in backend modules (rate limiting, payments, and more) that
live inside your Convex project.
