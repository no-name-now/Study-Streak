TOPIC 1 — INTRODUCTION TO IOT AND EDGE COMPUTING (LECTURE 1)
Deck: Lecture 1, “IoT and Edge Computing” (PAU-CSC 418, Lino Isawhe). Learning objectives (from slides): (1) IoT fundamentals — characteristics, components, ecosystems; (2) cloud capabilities — scalable storage, trade-offs such as latency and bandwidth; (3) edge computing — local processing for low latency and mission-critical decisions; (4) the trifecta — combine IoT, edge and cloud into one architecture: Connect, Respond, Scale; (5) practical use cases — autonomous vehicles, smart farming, healthcare; (6) architecture myths.
In simple words: IoT connects physical things to networks so they can sense and act. Cloud gives huge, rentable computing and storage far away. But sending everything to a distant cloud causes two problems: latency (delay) and bandwidth (too much data). Edge computing fixes this by processing data near where it is produced. Together they form a “trifecta”: IoT connects, edge responds, cloud scales.
Sensors (IoT) produce data → Gateway/network carries it → Edge handles time-critical decisions locally → Cloud stores, analyses and scales → Applications show results and trigger actions
1.1 The Human-Body Analogy
HIGH PRIORITY — the lecturer’s anchor picture for the whole course.
FROM MY MATERIAL: touching a hot object: skin senses heat, nerves carry signals, a reflex jerks the hand away instantly, and the brain processes the experience for long-term memory.

FROM MY MATERIAL (core insight): “IoT produces the data, Edge processes time-critical events locally, and Cloud stores, analyzes and provides large scale computing resources.”
The basic idea (from slides): IoT is about connecting things. Edge computing is about processing information close to where it is produced. Cloud computing is about providing large-scale computing and storage resources.
Why the analogy works: your hand moves before your brain has finished thinking about the pain. Likewise a car must brake before a cloud server could reply. Fast, simple reactions happen locally; slow, deep thinking happens centrally.
Exam use: “Which part of the body corresponds to edge computing?” → local reflexes. “Which corresponds to the gateway?” → nervous system (carries information), not the brain.
1.2 What Is the Internet of Things?
HIGH PRIORITY
1.2.1 Definition
KEYWORDS: network of physical objects, embedded, sensors, software, processing, communication technologies, collect and exchange data
DEFINITION — Internet of Things (IoT)
Formal definition (from slides): a network of physical objects or “things” embedded with sensors, software, processing capabilities and communication technologies that enable them to collect and exchange data over a network.
Plain-English meaning: ordinary objects that can sense the world, think a little, and talk over a network.
Exam version: physical objects + embedded sensors/software/processing/communication + collect and exchange data over a network.
Memory hook (slide’s own formula): “Physical things + Sensors + Connectivity + Data + Action = IoT.”
FROM MY MATERIAL — examples of IoT “things”: vehicles; farm equipment; medical devices; wearable devices; home appliances; security systems; environmental sensors.
1.2.2 What makes something “IoT”? Traditional vs IoT thermometer
FROM MY MATERIAL:
Traditional thermometer: Temperature → Display → Human reads it.
IoT temperature sensor: Temperature → Sensor → Processing → Network → Edge/Cloud → Application → Action.
An IoT system can collect data automatically, transmit data, process data, trigger an action, and communicate with other systems.

The test for “is it IoT?”: does it sense, connect (exchange data over a network) and lead to data-driven action without a person manually reading a display? A digital thermometer with a screen but no network is not IoT.
Checking for understanding (slide 10) — is a smartwatch IoT? Yes. ADDITIONAL CONTEXT — model answer: a normal wristwatch only shows the time. A smartwatch has sensors (heart rate, accelerometer), processing and connectivity (to a phone and the internet), so it collects and exchanges data and can trigger actions (notifications, activity alerts). It matches every part of “things + sensors + connectivity + data + action”.

1.3.3 Gateways
KEYWORDS: bridge, physical device or software, translating communication languages, routing data, secure
DEFINITION — Gateway
Formal definition (from slides): a gateway acts as a bridge between devices and other networks or computing systems. It can be a physical device or a software program that serves as a secure bridge between local smart devices and the cloud, translating different communication languages and routing data.
Plain-English meaning: the translator and post office between your local gadgets and the internet.
Example: ZigBee door sensors cannot speak to the internet directly. A gateway receives their ZigBee messages, translates them into IP/MQTT messages and forwards them to the cloud (protocols in Topic 3).
Trap: a gateway can be software, not only a box.

1.5 The Two Problems with Sending Everything to the Cloud
HIGH PRIORITY — the reason edge computing exists.
1.5.1 Latency
KEYWORDS: delay between sending information and receiving a response; milliseconds; self-driving car
DEFINITION — Latency
Formal definition (from slides): the delay between sending information and receiving a response.
FROM MY MATERIAL (example): a self-driving car detects an obstacle. Path via cloud: Car → Internet → Cloud → Processing → Internet → Car → Brake. “The delay may be unacceptable.” For some applications a delay of several seconds may be acceptable; for others, milliseconds can be critical.
ADDITIONAL CONTEXT (why milliseconds matter): at 100 km/h a car travels about 27.8 metres per second, so every 100 ms of delay is roughly 2.8 metres travelled before braking starts.
1.5.2 Bandwidth
KEYWORDS: maximum rate of data transmission, bits per second (bps), raw video, congestion
DEFINITION — Bandwidth
Formal definition (from slides): the maximum rate at which data can be transmitted over a network connection, usually measured in bits per second (bps).
FROM MY MATERIAL (example): thousands of cameras continuously sending raw video: Camera → Huge amount of video → Internet → Cloud, causing high bandwidth consumption, increased costs, network congestion, unnecessary data transmission. “Do we really need to send everything to the cloud?”

1.6 Edge Computing
HIGH PRIORITY
1.6.1 Definition
KEYWORDS: distributed computing model, processing closer to the source, sensors, devices, local gateways, rather than relying entirely on centralised cloud
DEFINITION — Edge computing
Formal definition (from slides): a distributed computing model in which data processing occurs closer to the source of data generation, such as sensors, devices, or local gateways, rather than relying entirely on centralised cloud servers.
Plain-English meaning: do the urgent thinking nearby instead of sending everything far away.
Exam version: distributed + processing near the data source + not entirely reliant on the cloud.
Memory hook: “Edge = Early decision, Data stays close.”
FROM MY MATERIAL (core insight): “The edge handles immediate processing, while the cloud handles things like long-term storage, analytics, dashboards, and large-scale processing.”
Path
Flow (from slides)
Traditional cloud
CCTV camera → Local network → Internet → Cloud data centre → Processing
Edge computing
CCTV camera → Local network → Edge computer → Processing (often on the same local network)
Note the word “entirely”: edge computing does not remove the cloud; it stops relying entirely on it.
1.6.2 What counts as “the edge”?
FROM MY MATERIAL: “The edge is not necessarily one specific device. It refers to computing resources located near the source of data.” Examples: Raspberry Pi; industrial computer; smart gateway; local server; intelligent camera; vehicle computer.
Key point: “edge” is defined by location relative to the data, not by device type. A Raspberry Pi in a farm shed is edge; the same Raspberry Pi in a distant data centre would not be.
1.6.3 Why edge computing became necessary
FROM MY MATERIAL: “Data is increasingly generated far away from centralised cloud servers, and some applications need faster or more local processing.” Diagram: Sensors 1…N → EDGE (analyse locally; detect problems; send useful information) → CLOUD.

1.8 Topic 1 — Deeper Understanding
Problem solved by edge: cloud-only IoT is too slow for reflex decisions, too costly in bandwidth at scale, and exposes raw sensitive data.
What existed before: devices sending everything to a central server (or no network at all — the traditional thermometer).
Assumptions: the edge has enough local computing power; the cloud is still reachable for long-term work.
Limitations of edge: limited compute and storage; many devices to manage and secure; harder updates.
When NOT to use edge: a weekly report from a few sensors — latency and bandwidth don’t matter, so send it straight to the cloud.
What if conditions change? If network connectivity becomes unreliable (rural farm), edge becomes more important; if data is tiny and delays are fine, cloud-only is simpler.
1.9 Topic 1 — Tricky Exam Angles
Common traps
Saying edge computing replaces the cloud.
Saying edge computing guarantees privacy or security.
Confusing latency (delay) with bandwidth (capacity).
Calling the gateway the “brain” (it is the nervous system; the cloud is the brain).
Thinking the edge is one specific device.
Wording traps
“Computation performed in proximity to where data originates” → edge computing.
“Renting compute and storage over the internet” → cloud computing.
“Maximum throughput a link can carry” → bandwidth.
“Turning a fan on automatically above 30 °C” → self-adapting behaviour.
Concept traps
Sensor vs actuator; gateway vs edge; dynamic nature vs self-adapting; vertical vs horizontal scaling.
Scenario traps
“A factory has 400 vibration sensors; only anomalies need to reach head office.” → edge filtering (bandwidth).
“A hospital wants 10 years of patient vitals for research.” → cloud (long-term storage, analytics).
“A valve opens using compressed air in a bottling plant.” → pneumatic actuator.
Exception traps
A gateway can be software. The edge can be inside the device (intelligent camera).
For some applications, seconds of latency are acceptable.
“NOT” questions
“Which is NOT a key characteristic of IoT (per slides)?” → e.g. “centralisation”, “single vendor”.
“Which is NOT a benefit of edge computing on the slides?” → e.g. “unlimited storage”, “automatic security”.
“Which is NOT an actuator?” → e.g. GPS, camera, humidity sensor.
Comparison traps
Edge vs cloud; latency vs bandwidth; electric vs hydraulic vs pneumatic actuators.

1.11 Topic 1 — Things I Might Wrongly Think
❌ Incorrect idea: Edge computing replaces cloud computing.
✅ Correct understanding: The edge handles immediate processing; the cloud still provides storage, analytics and scale.
🧠 Why the confusion happens: New technologies are often presented as replacing old ones.
❌ Incorrect idea: Processing at the edge makes data secure.
✅ Correct understanding: Edge reduces raw-data transmission, but security and privacy must still be designed in.
🧠 Why the confusion happens: “Data stays local” sounds like “data is safe”.
❌ Incorrect idea: More bandwidth fixes latency.
✅ Correct understanding: Bandwidth is capacity; latency is delay; a wide link can still be far away.
🧠 Why the confusion happens: Both are described loosely as “internet speed”.
❌ Incorrect idea: The edge is a special kind of device.
✅ Correct understanding: It is any computing resource near the data source — a Pi, a gateway, a camera, a vehicle computer.
🧠 Why the confusion happens: Products are marketed as “edge devices”.
❌ Incorrect idea: Any digital gadget is IoT.
✅ Correct understanding: IoT needs sensing, connectivity, data exchange and action; a digital thermometer with only a display is not IoT.
🧠 Why the confusion happens: “Smart” and “digital” are used interchangeably in everyday speech.

In simple words: this lecture is a tour of where IoT is used. For each application you should be able to say: what problem it solves, which sensors collect data, what action follows (actuator or alert), and where the data goes (local controller, server or cloud). That four-part pattern lets you answer questions about applications you have never seen.
The universal pattern for every application: Sensors (what is measured) → Local node/controller/gateway → Server or cloud (aggregate, analyse) → Action (actuator, alert, app, decision)

2.2 Home Automation
HIGH PRIORITY
2.2.1 Smart lighting (homes)
FROM MY MATERIAL:
Purpose: save energy by adapting lighting to ambient conditions and switching on/off or dimming when needed.
Key enabling technologies: solid-state lighting (e.g. LEDs) and IP-enabled lights. For solid-state lighting, spectral and temporal characteristics can be configured.
How it saves energy: by sensing human movements and the environment and controlling lights accordingly.
Wireless/internet-connected lights can be controlled remotely from mobile or web apps.
Lights with occupancy and temperature sensors can change intensity and colour based on ambient conditions “to provide a good ambiance”.
ADDITIONAL CONTEXT — “spectral and temporal”: spectral = the light’s colour make-up (warm/cool); temporal = how it changes over time (dimming schedules, fades).
2.2.2 Smart appliances
FROM MY MATERIAL: each appliance having its own controls is cumbersome; smart appliances make management easier and give remote status information. Examples: smart washer/dryers (remote control; notify when the cycle is complete); smart thermostats (remote temperature control; learn user preferences); smart refrigerators (track items using RFID tags; alert when an item is low on stock).
2.2.3 Intrusion detection
FROM MY MATERIAL:
Uses security cameras and sensors such as PIR sensors and door sensors to detect intrusions and raise alerts (SMS or email). Advanced systems send an image grab or short video clip.
Cloud-controlled system: location-aware services — the geo-location of each node is detected and stored in the cloud; on intrusion, cloud services alert occupants, security post or local police.
UPnP-based system: uses image processing to recognise the intrusion and send an instant message.
ADDITIONAL CONTEXT: a PIR (passive infrared) sensor detects changes in infrared (body heat) to sense motion. UPnP (Universal Plug and Play) is a set of protocols that lets devices on a local network discover each other and their services automatically.
2.2.4 Smoke/gas detectors
FROM MY MATERIAL:
Smoke detectors detect smoke, an early sign of fire, using optical detection, ionisation or air sampling; they can signal a fire alarm system.
Gas detectors detect harmful gases such as carbon monoxide (CO) and liquid petroleum gas (LPG).
A smart smoke/gas detector can raise alerts in human voice describing where the problem is, and send SMS/email to the user or local fire safety department.

2.3 Smart Cities
HIGH PRIORITY
2.3.1 Smart parking
FROM MY MATERIAL:
Problem: finding parking in rush hour is slow and frustrating; drivers searching blindly create extra traffic congestion.
How it works: a sensor for each parking slot detects empty or occupied → information aggregated by a local controller → sent over the Internet to the database/back-end → drivers access it via smartphones, tablets, in-car navigation.
Slot sensors → Local controller (aggregates) → Internet → Back-end database → Driver apps
2.3.2 Smart lighting for roads
FROM MY MATERIAL: saves energy; lighting dynamically controlled and adaptive to ambient conditions; remotely configurable schedules and intensity; custom configurations for situations such as a foggy day or a festival; some lights have sensors and communicate with other lights to exchange ambient information.
CONTRADICTION / SLIDE ISSUE FLAG (statistic): the slide says “road lighting is responsible for 19% of global electricity use and around 6% of global greenhouse gas emissions.” The source figure (IEA, 2006) refers to all lighting, not road lighting. The IEA found that 19 percent of global electricity generation is taken for lighting (phys.org report on the IEA study), and the UN, citing the same report, gives some 19% of electricity consumption and 6% of CO2 emissions for lighting overall (optics.org). Outdoor lighting was only about 8% of lighting electricity in that breakdown (Earth Policy Institute, from IEA data). In an exam, quote the slide if asked “according to the lecture”, but know that the 19% is for lighting in general. (The slide also has the typo “roading lighting”.)
2.3.3 Smart roads
FROM MY MATERIAL: sensors provide road conditions, travel-time estimates, and alerts (poor driving conditions, congestion, accidents) → safer roads and fewer jams. Data goes via the Internet to cloud applications and social media and is sent to subscribing drivers. A distributed, autonomous sensor network can give a consistent view of the road “a few hundred meters ahead… or a few dozen miles away” so drivers react early.
2.3.4 Structural health monitoring (SHM)
FROM MY MATERIAL: a network of sensors monitors vibration levels in structures such as bridges and buildings. Analysis can detect cracks and mechanical breakdowns, locate damage, calculate the remaining life of the structure, and give advance warnings of imminent failure.
Key phrase: vibration is the measured quantity — a common MCQ distractor would be “temperature” or “water level”.

2.7 Agriculture
HIGH PRIORITY — both applications use sensors and actuators, which makes them good “full loop” examples.
2.7.1 Green house control
FROM MY MATERIAL: green houses have glass or plastic roofs. Sensors monitor temperature, humidity, soil moisture, light and carbon dioxide; conditions are controlled automatically using actuators (valves releasing water, switches controlling fans). Data is stored on central servers or the cloud to optimise control strategies and correlate productivity with strategies.
2.7.2 Smart irrigation
FROM MY MATERIAL: improves crop yields while saving water. Soil moisture sensors measure moisture; water flows through irrigation pipes only when moisture falls below a predefined threshold. Measurements are collected on a server or cloud to plan watering schedules.
Soil moisture sensor → threshold check (local) → valve opens/closes (actuator) → data to cloud → watering schedule planned
Link to Topic 1: the threshold decision is a natural edge job (fast, local, works without internet); schedule planning is a cloud job. It is also an example of self-adapting behaviour.

2.11 Topic 2 — Deeper Understanding
Problem solved: each domain shows IoT replacing manual observation (someone checking a river, a shelf, a field) with continuous automated sensing and quicker action.
Common assumption: sensors are reliable and connectivity exists — often weak in rural areas (agriculture, forests), which is a reason for edge processing.
Limitations: cost of many sensor nodes, power in remote places (forests, rivers), privacy (cameras in homes; location data in fleets), security (smart locks, payments).
When would IoT be inappropriate? When manual checks are cheap and rare, or when a wrong automatic action is dangerous and the sensing is unreliable.

Common traps
Saying structural health monitoring measures temperature (it is vibration).
Mixing fleet tracking (GPS, location) with shipment monitoring (conditions inside).
Thinking NFC does the bulk data transfer (Bluetooth does, after NFC pairing).
Quoting “road lighting = 19% of electricity” as fact without knowing it refers to all lighting.
Wording traps
“Sensors that measure vibration in bridges to predict remaining life” → structural health monitoring.
“Tags read by shelf-mounted readers” → RFID inventory management.
“Releasing water only below a moisture threshold” → smart irrigation.
Concept traps
RFID vs NFC vs Bluetooth; weather vs air pollution monitoring; green house control vs smart irrigation.

“A truck carrying tomatoes is re-routed because its container is too warm.” → shipment monitoring.
“A fridge texts you that milk is low.” → smart appliance (RFID).

✅ Correct understanding: Many only monitor and alert (weather, noise, floods, SHM); others also actuate (irrigation, green houses, lighting).

TOPIC 3 — EVOLUTION AND ARCHITECTURE OF IOT: THINGS, PROTOCOLS, LOGICAL DESIGN AND M2M (LECTURE 3)
Deck: Lecture 3, “Evolution and Architecture of IoT”. Content (from slides): what “things” are; IoT protocols by layer (link, network/internet, transport, application); the logical design of IoT (functional blocks, communication models, communication APIs); IoT and M2M.
In simple words: this is the “how does it talk?” lecture. A thing sends data down a stack of protocol layers: the link layer puts bits on a wire or radio; the network layer addresses and routes packets (IP); the transport layer delivers messages reliably (TCP) or quickly (UDP); the application layer decides the message format and style (HTTP, CoAP, MQTT…). On top of that, the logical design describes the system’s building blocks and the patterns by which parts communicate (request-response, publish-subscribe, push-pull, exclusive pair).
Application (HTTP, CoAP, WebSockets, MQTT, XMPP, DDS, AMQP) → Transport (TCP, UDP) → Network (IPv4, IPv6, 6LoWPAN) → Link (Ethernet, Wi-Fi, WiMAX, 802.15.4, cellular)
UNCLEAR FROM MATERIAL (title): despite “Evolution” in the title, no slide traces the history of IoT. The only historical element is IoT vs M2M (3.6), which “evolved from different backgrounds”. ADDITIONAL CONTEXT: the usual story is M2M (machines linked over private/proprietary networks for monitoring) → IP-connected devices → cloud-based IoT with analytics → edge + cloud (Topic 1).
3.1 Things in IoT
HIGH PRIORITY
KEYWORDS: unique identities, remote sensing, actuating, monitoring, exchange data, process locally or centrally, temporal and space constraints, interfaces
DEFINITION — “Things” in IoT
Formal definition (from slides): devices which have unique identities and can perform remote sensing, actuating and monitoring capabilities.
Plain-English meaning: each thing can be told apart from every other (an ID/address), and it can sense, act or be watched from afar.
Exam version: unique identity + sensing / actuating / monitoring.
FROM MY MATERIAL:
IoT devices exchange data with other devices and applications directly or indirectly.
They may process data locally, send it to centralised servers or cloud back-ends, or split tasks between local and infrastructure processing, “based on temporal and space constraints (i.e., memory, processing capabilities, communication latencies and speeds, and deadlines).”
Device interfaces (wired and wireless): (i) I/O interfaces for sensors; (ii) interfaces for Internet connectivity; (iii) memory and storage interfaces; (iv) audio/video interfaces.
Device types vary: wearable sensors, smart watches, LED lights, automobiles, industrial machines. Almost all generate data that, processed by analytics, guides actions locally or remotely.
Link to Topic 1: “temporal and space constraints” are the edge vs cloud decision in formal language — deadlines and latency push work to the edge; memory and processing limits push work to the cloud.
Memory hook for the four interfaces: “S-I-M-A: Sensors I/O, Internet, Memory/storage, Audio/video.”

REST-based communication APIs
DEFINITION — REST (Representational State Transfer)
Formal definition (from slides): a set of architectural principles for designing web services and web APIs that focus on a system’s resources and how resource states are addressed and transferred. REST APIs follow the request-response model.
FROM MY MATERIAL — REST constraints:
Constraint
Meaning (from slides)
Benefit
Client-server
Separation of concerns: clients don’t handle data storage; servers don’t handle the user interface

Stateless
Each request carries all information needed; no stored context on the server; session state kept entirely on the client
Simpler, scalable servers
Cache-able

Unlike REST, no new connection for each message.
Begins with a connection setup request from the client (the WebSocket handshake), sent over HTTP, which the server treats as an upgrade request; if supported, the server responds.
After setup, both sides send messages in full-duplex mode.
Reduces network traffic and latency (no setup/teardown per message); suits IoT apps with low-latency or high-throughput requirements.

DEFINITION — Machine-to-Machine (M2M)
Formal definition (from slides): networking of machines (or devices) for remote monitoring, control and data exchange.
FROM MY MATERIAL:
IoT and M2M are “often used interchangeably”, but they “evolved from different backgrounds”.
An M2M area network has M2M nodes with embedded hardware for sensing, actuation and communication.

3.6 Topic 3 — Deeper Understanding
Problem solved by layering: each layer can change independently — a device can switch from Wi-Fi to cellular (link) without changing MQTT (application).
Why IoT-specific protocols (CoAP, MQTT, 6LoWPAN) exist: HTTP/TCP/IPv6 were designed for powerful computers on fast networks; constrained devices need smaller headers, fewer handshakes and lower power.
Assumption of publish-subscribe: the broker is always available — it is a single point of failure unless replicated.
When NOT to use UDP: when every message must arrive in order and nothing at a higher layer adds reliability (e.g. firmware updates).
What if the network is unreliable? Push-pull queues buffer messages; MQTT brokers can retain messages; stateless REST requests can simply be retried.
3.7 Topic 3 — Tricky Exam Angles
Common traps
Putting 6LoWPAN in the link layer (it is network layer; it works with 802.15.4).
Saying CoAP runs on TCP (it runs on UDP).
Calling MQTT request-response (it is publish-subscribe).
Saying REST is stateful or WebSocket is stateless (the reverse).
Confusing ZigBee with 802.15.4.
Wording traps
“Producers place messages in a buffer that consumers drain at their own pace” → push-pull.
“A long-lived, two-way channel where the server tracks open connections” → exclusive pair.
“Each call carries everything the server needs to understand it” → REST stateless constraint.
“The client cannot tell whether it talks to an intermediary” → REST layered system.
Concept traps
TCP vs UDP; HTTP vs CoAP; MQTT vs XMPP; flow control vs congestion control; logical vs physical design.
Scenario traps
“Thousands of sensors publish readings; several apps need them.” → publish-subscribe (MQTT).
“A sensor sends one tiny reading every minute and must save power; occasional loss is acceptable.” → UDP/CoAP.
“Industrial meters on a factory floor use ModBus and are read by a central system.” → M2M.
Exception traps
WebSocket’s handshake is sent over HTTP, then upgraded.
CoAP is UDP-based yet still request-response and easily maps to HTTP.
“NOT” questions
“Which is NOT a transport-layer function on the slides?” → e.g. “host addressing” (network layer).
“Which is NOT a REST constraint on the slides?” → e.g. “stateful sessions”, “publish-subscribe”.
“Which is NOT a link-layer standard?” → e.g. IPv6, 6LoWPAN, TCP.
“Which is NOT an IoT functional block?” → e.g. “Database”, “Compiler”.
Comparison traps
Publish-subscribe vs push-pull; REST vs WebSocket APIs; IPv4 vs IPv6; IoT vs M2M.

3.9 Topic 3 — Things I Might Wrongly Think
❌ Incorrect idea: CoAP runs over TCP because it is “like HTTP”.
✅ Correct understanding: CoAP is request-response like HTTP but runs over UDP for constrained devices.
🧠 Why the confusion happens: Its similarity to HTTP suggests the same transport.
❌ Incorrect idea: ZigBee and 802.15.4 are the same thing.
✅ Correct understanding: 802.15.4 is the low-rate link-layer standard; ZigBee is a higher-level protocol built on it.
🧠 Why the confusion happens: They are almost always mentioned together.
❌ Incorrect idea: UDP is simply worse than TCP.
✅ Correct understanding: UDP avoids handshake overhead and suits small, time-sensitive messages; reliability can be added higher up.
🧠 Why the confusion happens: “Unreliable” sounds like “broken”.
❌ Incorrect idea: Publish-subscribe and push-pull are the same pattern.
✅ Correct understanding: Pub-sub broadcasts topic data to all subscribers via a broker; push-pull uses queues that consumers pull from, buffering rate mismatches.
🧠 Why the confusion happens: Both decouple producers from consumers.
❌ Incorrect idea: MQTT means “Message Queue Telemetry Transport”.
✅ Correct understanding: Since 2013 the official name is just “MQTT”; it originally meant MQ Telemetry Transport, and it does not use message queues.
🧠 Why the confusion happens: The expansion is widely repeated, including on the slide.
TOPIC 4 — EMBEDDED SYSTEMS FUNDAMENTALS (LECTURE 4)
Deck: Lecture 4, “Embedded Systems Fundamentals”. Content (from slides): what an embedded system is; embedded vs general-purpose computers; the input → processing → output model; key components; the four categories of core (processors, ASIC, PLD, COTS); microprocessor vs microcontroller; DSP; ASIC; PLD/FPGA; communication interfaces (I²C, SPI, UART…); classification by triggering, by deterministic behaviour (soft/hard real-time) and by complexity (small, medium, large scale).
In simple words: every IoT “thing” has a small computer built into it, designed to do one job well — that is an embedded system. 4.1 What Is an Embedded System?
HIGH PRIORITY

KEYWORDS: computer-based system, hardware and software, integrated into a larger device, specific task or closely related functions

Formal definition (from slides): a computer-based system that entails both hardware and software, designed and integrated into a larger device or product to perform a specific task/function or set of closely related functions.

4.6 Other Processing Cores: DSP, ASIC, PLD/FPGA
HIGH PRIORITY
4.6.1 Digital Signal Processor (DSP)
FROM MY MATERIAL: a processor optimised for mathematical operations on digital signals; useful for audio, video and communication signals; contains program memory, data memory, computational engine and I/O unit; for computationally intensive signal processing (audio, video, telecommunications).
ADDITIONAL CONTEXT: DSPs are fast at repeated multiply-and-add operations used in filters and Fourier transforms — e.g. noise cancellation in earbuds.
4.6.2 Application-Specific Integrated Circuit (ASIC)
FROM MY MATERIAL: an IC designed for a particular application or function. Advantages: high performance and optimisation. Limitations: high development cost and less flexibility after fabrication.
ADDITIONAL CONTEXT: examples include Bitcoin mining chips and the custom chips inside many mass-produced gadgets. Worth it only at high volume, because design costs are huge but per-unit costs are low.
4.6.3 Programmable Logic Device (PLD) and FPGA
FROM MY MATERIAL:
A PLD is an IC whose logic functionality can be configured or programmed by the designer. Examples: CPLD and FPGA.
An FPGA is a programmable digital logic device with configurable logic resources and interconnections that can be programmed to implement specific digital hardware functions.
FPGAs are useful for hardware acceleration, parallel processing, specialised digital logic, high-speed processing and reconfigurable hardware.
ADDITIONAL CONTEXT: FPGA = Field-Programmable Gate Array; CPLD = Complex Programmable Logic Device. Programming an FPGA means describing hardware (in VHDL or Verilog), not writing a step-by-step program.

4.9 Topic 4 — Deeper Understanding
Problem solved: dedicated computers make products cheaper, smaller, more reliable and lower-power than putting a PC inside.
Why so many core types? Trade-off triangle: performance (ASIC, FPGA, MPU), flexibility (MCU, MPU, FPGA) and cost/volume (ASIC cheap only at volume, MCU cheap always).
Assumption: the function is known in advance; if requirements change often, flexible cores (MCU, FPGA) beat fixed ones (ASIC).
When NOT to use an MCU: heavy video processing, machine learning on images, full Linux software stacks → MPU/SBC or accelerator.
When NOT to use an ASIC: low volumes or changing requirements.
What if a deadline is missed? In soft real-time, quality drops; in hard real-time, the system has failed — design must guarantee timing (RTOS, time-triggered scheduling).
4.10 Topic 4 — Tricky Exam Angles
Common traps
Calling a Raspberry Pi a microcontroller.
Saying an ASIC can be reprogrammed (FPGAs can; ASICs can’t after fabrication).
Saying UART uses a clock line.
Equating real-time with “fast”.
Forgetting that DSPs and FPGAs also appear as processing options in the I-P-O model.
Wording traps
“A processor that depends on separate memory chips and I/O controllers” → microprocessor.
“Processor, RAM, flash and peripherals integrated in one package for a dedicated control job” → microcontroller.
“Logic whose function the engineer can rewire after manufacture” → PLD/FPGA.
“A late result is tolerable within limits” → soft real-time.
Concept traps
MPU vs MCU; ASIC vs FPGA; event-triggered vs time-triggered; SBC vs MCU board; chip-level vs external interfaces.
Scenario traps
“An airbag must fire within 30 ms of impact.” → hard real-time.
“A display needs fast data from the controller.” → SPI.
“Five sensors share two wires, each with its own address.” → I²C.
“A company making 10 million identical fitness bands wants the cheapest, most efficient chip.” → ASIC.
“NOT” questions
“Which is NOT one of the four categories of embedded core?” → e.g. “GPU cluster”, “cloud server”.
“Which is NOT a microcontroller family on the slides?” → e.g. “Cortex-A76”, “Intel Core i7”.
“Which is NOT a chip-level interface?” → e.g. USB, Wi-Fi, RS-485.
Comparison traps
Small vs medium vs large scale; soft vs hard real-time; DSP vs MCU.

4.12 Topic 4 — Things I Might Wrongly Think
❌ Incorrect idea: A Raspberry Pi is a microcontroller.
✅ Correct understanding: It is a microprocessor-based single-board computer running Linux; Arduino and ESP32 boards are MCUs.
🧠 Why the confusion happens: Both are small, cheap boards used in the same hobby projects.
❌ Incorrect idea: Real-time means extremely fast.
✅ Correct understanding: Real-time means guaranteed to meet deadlines; hard real-time misses are catastrophic.
🧠 Why the confusion happens: “Real time” in everyday speech means “instant”.
❌ Incorrect idea: ASICs and FPGAs are the same because both are hardware logic.
✅ Correct understanding: ASICs are fixed and optimised; FPGAs are reprogrammable.
🧠 Why the confusion happens: Both implement custom digital logic.
❌ Incorrect idea: All serial interfaces need a clock.
✅ Correct understanding: UART is asynchronous and needs no shared clock; SPI and I²C are clocked.
🧠 Why the confusion happens: SPI and I²C are learned together with UART.
❌ Incorrect idea: Embedded systems are always tiny and weak.
✅ Correct understanding: Resources are chosen for the application; large-scale embedded systems use 64-bit multi-core processors.
🧠 Why the confusion happens: Classic examples are watches and microwaves.

5.3 Shared Responsibility
HIGH PRIORITY
FROM MY MATERIAL:
“Cloud security is shared between the provider and customer.”
Azure operates the underlying cloud infrastructure; customers remain responsible for configuration decisions, identities, data, application code and permissions.
“The exact division depends on the service model.”
Service model
Typical customer responsibility (from slides)
IaaS
Operating system configuration and patching, application software, identities, data and network rules
PaaS
Application code, data, identities and service configuration; Azure manages more of the platform
Managed containers / serverless
Application logic, images or function code, permissions, data and deployment settings
Pattern: moving from IaaS → PaaS → serverless, the customer manages less (the OS disappears from the customer’s list), but data, identities and permissions always stay with the customer.
ADDITIONAL CONTEXT: IaaS = Infrastructure as a Service (you rent VMs); PaaS = Platform as a Service (you deploy code to a managed platform); SaaS = Software as a Service (you use finished software — not on the slide). 5.10 Topic 5 — Deeper Understanding
Problem solved: turns “the cloud” from an idea into concrete, secure, organised, repeatable resources.
Why IaC? Manual portal clicks can’t be reviewed or reproduced exactly; files can be versioned, reviewed and re-run.
Assumption of shared responsibility: customers understand which layers they own; most cloud breaches come from customer misconfiguration (open ports, leaked secrets).
When NOT to use a VM: for a stateless web API that only needs to run code — containers or serverless reduce operational work.
When NOT to use containers: when the workload needs its own OS, kernel modules or legacy Windows features.
Link to IoT: telemetry from devices (Topic 1) lands in storage (Blob, SQL), is processed by compute (Functions, containers), is protected by identity, and watched by monitoring.

Common traps
Confusing region with availability zone.
Thinking Azure is responsible for patching your VM’s OS (in IaaS you are).

Saying containers have their own guest OS.

Wording traps
“A container that groups resources so they can be managed as one unit” → resource group.
“The ability to release resources automatically when demand drops” → elasticity.
“Describing infrastructure in versioned files” → IaC.
“The layer through which all create/update/delete requests flow” → ARM.
Concept traps
IaaS vs PaaS vs serverless responsibilities; portal vs CLI vs templates vs pipeline; VM vs container.
Scenario traps
“A bank must run a 2009 Windows application unchanged in the cloud.” → VM (IaaS, legacy compatibility).
“A team wants identical deployments of its microservice to test and production.” → containers + IaC/CI/CD.
“An admin manually added servers in December and never removed them.” → scalable but not elastic.
“A developer stores a database password in a Git repository.” → violates the VM security checklist (use a secret-management service such as Key Vault).
“NOT” questions
“Which is NOT an Azure monitoring service on the slides?” → e.g. Key Vault, Load Balancer.
“Which is NOT a step in the provisioning process?” → e.g. “write the user manual”.
“Which is NOT a customer responsibility in PaaS?” → e.g. “patching the platform’s operating system”.
Comparison traps
Manual vs automated provisioning; scalability vs elasticity; VM vs container.

5.13 Topic 5 — Things I Might Wrongly Think
❌ Incorrect idea: Moving to the cloud makes security the provider’s problem.
✅ Correct understanding: Security is shared; customers always own their data, identities, permissions and configuration.
🧠 Why the confusion happens: Providers advertise how secure their data centres are.
❌ Incorrect idea: Scalability and elasticity are synonyms.
✅ Correct understanding: Elasticity adds automatic scaling down when demand falls.
🧠 Why the confusion happens: Both describe “handling more users”.
❌ Incorrect idea: A container is a small virtual machine.
✅ Correct understanding: A container shares the host kernel and isolates processes; a VM has its own guest OS.
🧠 Why the confusion happens: Both are “isolated environments” in diagrams.
❌ Incorrect idea: Clicking in the portal is as good as IaC.
✅ Correct understanding: Portal work is hard to reproduce and causes drift; IaC is declarative, reviewable and repeatable.
🧠 Why the confusion happens: The portal is easier for learning.
❌ Incorrect idea: A region and an availability zone are the same.
✅ Correct understanding: A zone is a physically separate location inside a region.
🧠 Why the confusion happens: Both are “places where Azure runs”.
TOPIC 6 — CHOOSING THE RIGHT BOARD (EDGE DEVICE) FOR YOUR PROJECT (LECTURE 9)
Deck: Lecture 9, “Choosing the Right Board [Edge Device] for Your Project”. Content (from slides): MCU vs SBC decision; five selection parameters; detailed profiles of the Arduino Uno, Arduino Mega 2560, Raspberry Pi 5 and ESP32; class activity (blinking LED on an Arduino Mega).
In simple words: before buying hardware, decide whether the job needs a microcontroller (MCU) — cheap, low-power, simple real-time control — or a single-board computer (SBC) — a small Linux computer for heavy computing. 6.3 Arduino Uno
HIGH PRIORITY
FROM MY MATERIAL: powered by the ATmega328P microcontroller; designed for low-complexity, real-time control applications.
Parameter
Arduino Uno (from slides)
Processing
R3: Microchip ATmega328P, 8-bit AVR RISC, 16 MHz, 2 KB SRAM, 32 KB flash. R4 Minima: Renesas RA4M1 (32-bit Arm Cortex-M4 with FPU) @ 48 MHz, 32 KB SRAM, 256 KB flash
Connectivity
USB (Type-B or Type-C) for programming/serial. No native Wi-Fi or Bluetooth; needs expansion shields
GPIO & interfaces
14 digital I/O (6 PWM); 6 analogue inputs (ADC); 1× UART, 1× SPI, 1× I2C; 5 V logic (R3/R4)
Power
Very low: ~45 mA (~0.22 W) at 5 V; sleep modes down to the microampere range
Ideal applications
Sensors & actuators (temperature, ultrasonic, PIR; relays, servos, LEDs); basic automation (line-following/obstacle-avoiding robots, home automation triggers, switch controllers)
ADDITIONAL CONTEXT — checking the power figure: P = V × I = 5 V × 0.045 A = 0.225 W ≈ 0.22 W, matching the slide.

6.5 Raspberry Pi 5
HIGH PRIORITY
FROM MY MATERIAL: “Unlike microcontrollers that run bare-metal code, the Raspberry Pi 5 is a fully realised Single Board Computer (SBC). It executes full operating systems (primarily Linux) and targets high-performance computing tasks.”
Parameter
Raspberry Pi 5 (from slides)
Ease of learning
Moderate to advanced — needs Linux configuration, terminal, system permissions, and high-level languages (Python, C++, JavaScript)
Processing
Broadcom BCM2712, quad-core 64-bit Arm Cortex-A76 @ 2.4 GHz; 4, 8 or 16 GB LPDDR4X; storage via microSD / PCIe 2.0 (NVMe SSD)
Connectivity
Dual-band (2.4/5 GHz) 802.11ac Wi-Fi; Bluetooth 5.0 & BLE; Gigabit Ethernet (PoE+ via HAT); 2× USB 3.0, 2× USB 2.0; 2× 4K60 micro-HDMI; PCIe Gen 2.0
GPIO & interfaces
40-pin GPIO header (3.3 V logic); configurable UART, SPI, I2C, I2S; no onboard ADC (needs an external ADC IC for analogue); 2× 4-lane MIPI camera/display
Power
High (requires active management): idle ~2.7–3.0 W; full load 8–12 W+; needs a dedicated 5 V/5 A supply and active fan cooling
Exam traps:
No ADC on the Pi — to read an analogue sensor (e.g. a potentiometer or many soil-moisture probes) you need an external ADC chip. The Uno, Mega and ESP32 all have ADCs.
3.3 V logic — connecting a 5 V Arduino output directly to a Pi pin can damage it.
The Pi uses watts; the Arduinos use fractions of a watt.
ADDITIONAL CONTEXT: BLE = Bluetooth Low Energy; PoE = Power over Ethernet (power and data on one cable); HAT = “Hardware Attached on Top” add-on board; MIPI = the camera/display interface standard; I2S = a serial interface for digital audio.
6.6 ESP32 (Espressif Systems)
HIGH PRIORITY — “the dominant platform for IoT applications” (slide).
FROM MY MATERIAL: a low-power system-on-a-chip (SoC) microcontroller with integrated wireless.
Parameter
ESP32 (from slides)
Ease of learning
Moderate — works with Arduino IDE (C/C++), MicroPython and ESP-IDF (C framework); watch 3.3 V logic and pin multiplexing quirks
Processing
Tensilica Xtensa dual-core 32-bit LX6 @ up to 240 MHz; 520 KB SRAM; 4–16 MB external SPI flash; Ultra-Low-Power (ULP) co-processor
Connectivity
On-chip Wi-Fi 802.11 b/g/n (up to 150 Mbps); on-chip Bluetooth v4.2 BR/EDR and BLE
GPIO & interfaces
~34 GPIO (3.3 V, not 5 V tolerant); 18 channels 12-bit ADC, 2 channels 8-bit DAC; touch-capacitive pins; 3× UART, 2× SPI, 2× I2C, 2× I2S, PWM
Power
Highly dynamic / ultra-low-power optimised: Wi-Fi TX 160–260 mA (~0.8–1.3 W); idle ~20–50 mA; deep sleep ~10–15 µA (multi-year battery life)
Why the ESP32 dominates IoT (reasoning from the table): it combines MCU-level power (µA deep sleep) with built-in Wi-Fi and Bluetooth, a 32-bit dual-core CPU and many interfaces — no shields needed.
ADDITIONAL CONTEXT — why deep sleep matters (illustrative calculation): a 2,000 mAh battery at 15 µA (0.015 mA) would last about 2,000 ÷ 0.015 ≈ 133,000 hours ≈ 15 years in pure deep sleep; at 45 mA (an always-on Uno), about 44 hours. Real devices wake to measure and transmit, so practical life is shorter, but this is why the slide says “multi-year battery operation”.

6.8 Class Activity: Blinking LED on the Arduino Mega
HIGH PRIORITY — the slide’s code contains a bug.
FROM MY MATERIAL: students download the Arduino IDE and run this sample:
void setup() {
  // put your setup code here, to run once:
  pinMode(6,OUTPUT);
}
void loop() {
  // put your main code here, to run repeatedly:
  digitalWrite(6,HIGH);
  delay(1000);
  digitalWrite(12,LOW);
  delay(1000);
}
CONTRADICTION / SLIDE ISSUE FLAG (code bug): the LED is on pin 6, but the loop writes LOW to pin 12. Pin 6 is set HIGH and never set LOW, so the LED turns on and stays on — it does not blink. (Pin 12 was never set as an output, so writing to it does not affect the LED.) Corrected loop:
void loop() {
  digitalWrite(6, HIGH);   // LED on
  delay(1000);             // wait 1 second
  digitalWrite(6, LOW);    // LED off
  delay(1000);             // wait 1 second
}
How an Arduino sketch works:
Part
Runs
Purpose

Once, at power-up/reset
Configure pins (pinMode), start serial, etc.
loop()
Repeatedly, forever
The main behaviour

—

—

—
Pauses for the given milliseconds (1000 = 1 s)
One blink cycle: 1 s on + 1 s off = 2 s period → 0.5 Hz (one blink every two seconds).
Link to Topic 4: this is input → processing → output in its simplest form: no input; the MCU’s loop is the processing; the LED is the output. It is time-triggered behaviour (fixed delays).
ADDITIONAL CONTEXT — hardware: an external LED needs a current-limiting resistor (e.g. 220–330 Ω) in series between the pin and the LED, with the LED’s shorter leg (cathode) to GND.
6.9 Topic 6 — Deeper Understanding
Problem solved: prevents “hardware misallocation” — overpaying in money, power and complexity, or under-buying and hitting limits.
Assumptions: you know the workload (sensors, data rates, processing) and power source (mains vs battery) before choosing.
Limitations of MCUs: tiny RAM (2 KB on the Uno), no OS, limited libraries for heavy tasks.
Limitations of SBCs: high power, needs cooling, longer boot, SD-card corruption risk on power loss, a full OS to secure and update.
Common real design: ESP32 nodes (sensing, low power) + Raspberry Pi gateway (edge processing) + Azure (cloud) — exactly the trifecta of Topic 1 with the cloud of Topic 5.
What if the power source changes? On mains power, the Pi’s watts don’t matter; on a small battery, the ESP32’s µA deep sleep becomes decisive.
6.10 Topic 6 — Tricky Exam Angles
Common traps
Saying the Arduino Uno has built-in Wi-Fi.
Saying the Raspberry Pi can read analogue sensors directly.
Saying the ESP32 is 5 V tolerant.
Calling the Raspberry Pi a microcontroller.
Missing the pin-6/pin-12 bug in the blink code.
Wording traps
“Runs bare-metal firmware with kilobytes of RAM” → MCU (Uno/Mega).
“SoC microcontroller with integrated Wi-Fi and Bluetooth” → ESP32.
“Executes a full Linux operating system” → Raspberry Pi 5 (SBC).
“Same workflow as the Uno but with 54 digital pins” → Mega 2560.
Concept traps
MCU vs SBC; 5 V vs 3.3 V logic; ADC vs DAC; UART count (Uno 1, Mega 4, ESP32 3).
Scenario traps
“A battery-powered weather node must last a year and send data over Wi-Fi.” → ESP32 (deep sleep + Wi-Fi).
“A student wants to run a Python object-detection model on a camera feed.” → Raspberry Pi 5.
“A project needs to read 12 analogue sensors and 3 serial modules without wireless.” → Mega 2560 (16 analogue inputs, 4 UARTs).
Exception traps
The Uno R4 Minima is 32-bit Arm Cortex-M4 at 48 MHz — not every Uno is an 8-bit AVR.
The ESP32’s power is “highly dynamic”: high while transmitting, tiny in deep sleep.
“NOT” questions
“Which is NOT one of the five selection parameters?” → e.g. “board colour”, “brand popularity” (note: community is a parameter).
“Which board does NOT have an onboard ADC?” → Raspberry Pi 5.
“Which board does NOT have native wireless?” → Uno and Mega.
Comparison traps
Uno vs Mega; ESP32 vs Pi 5; idle vs load power.

6.12 Topic 6 — Things I Might Wrongly Think
❌ Incorrect idea: A Raspberry Pi is always the better choice because it is more powerful.
✅ Correct understanding: For simple control or battery projects it is overkill (hardware misallocation); MCUs are cheaper, simpler and far lower-power.
🧠 Why the confusion happens: More power feels like more capability.
❌ Incorrect idea: Every Arduino can talk to Wi-Fi.
✅ Correct understanding: The Uno and Mega need shields; the ESP32 has Wi-Fi and Bluetooth on-chip.
🧠 Why the confusion happens: Many online projects use “Arduino” loosely for ESP32 boards too.
❌ Incorrect idea: The Raspberry Pi can read any sensor.
✅ Correct understanding: It has no onboard ADC, so analogue sensors need an external ADC.
🧠 Why the confusion happens: It has far more features than an Arduino, so it seems to have everything.
❌ Incorrect idea: 3.3 V and 5 V boards can be wired together freely.
✅ Correct understanding: The ESP32 and Pi use 3.3 V logic; 5 V signals can damage them.
🧠 Why the confusion happens: All the pins look the same.
❌ Incorrect idea: The slide’s blink code blinks the LED.
✅ Correct understanding: It sets pin 6 HIGH and writes LOW to pin 12, so the LED on pin 6 stays on.
🧠 Why the confusion happens: The code looks right at a glance and matches the familiar Blink pattern.

EXAM ANSWER KEY
Section A — Answers
1. A network of physical objects embedded with sensors, software, processing capabilities and communication technologies that collect and exchange data over a network. Physical things + sensors + connectivity + data + action = IoT.
2. A distributed computing model in which data processing occurs closer to the source of data generation (sensors, devices, local gateways) rather than relying entirely on centralised cloud servers.
3. Latency: the delay between sending information and receiving a response. Bandwidth: the maximum rate at which data can be transmitted over a network connection, measured in bits per second.
4. A physical device or software program that acts as a secure bridge between local smart devices and other networks/the cloud, translating communication protocols and routing data.
5. Networking of machines for remote monitoring, control and data exchange. M2M area networks use proprietary or non-IP protocols (ModBus, M-Bus, ZigBee…); the communication network connecting to remote M2M areas is IP-based.
6. A computer-based system of hardware and software, designed and integrated into a larger device or product to perform a specific task or set of closely related functions.
7. Microcontroller: an IC combining a processor core with memory and peripheral interfaces, typically on one chip, for a specific control function. Microprocessor: a processor IC that performs computation but normally needs external memory and I/O to form a complete system.
8. Hard: missing a deadline can have catastrophic consequences (financial, loss of life). Soft: missing a deadline may not be critical and can be tolerated to a degree.
9. Resource group: a logical container to manage resources as a single unit. Region: a geographic area containing Azure data centres. Availability zone: a physically separate location within a region designed to improve resilience.
10. Scalability: the ability to handle increased workload by adding resources or improving capacity. Elasticity: the ability to adjust resources as demand changes, including scaling down when demand falls.
Section B — Answers
1. Skin/eyes detect stimuli (sensors); nerves carry signals (gateways/network); reflexes react instantly (edge); the brain thinks and stores long-term (cloud). IoT produces data, the edge handles time-critical events locally, the cloud stores, analyses and scales.
2. Data is increasingly produced far from cloud servers. Round trips to the cloud add delay that can be unacceptable (a self-driving car must brake in milliseconds), and sending everything (e.g. raw video from thousands of cameras) consumes bandwidth, raises costs and congests networks. The edge decides locally and sends only useful information (100 GB → 2 GB).
3. Publish-subscribe: publishers send data to topics managed by a broker, which delivers it to all subscribers; publishers don’t know consumers. Push-pull: producers push into queues and consumers pull when ready; the queue decouples them and buffers rate mismatches.
4. Constrained devices have little memory, processing and power, and use low-rate radios. CoAP is a request-response web protocol over UDP (no TCP handshakes) that maps easily to HTTP; 6LoWPAN compresses IPv6 datagrams so they fit low-power 802.15.4 networks.
5. Azure runs the underlying infrastructure; customers own configuration, identities, data, code and permissions. In IaaS the customer also patches and configures the OS; in PaaS Azure manages more of the platform; in serverless/managed containers the customer handles code/images, permissions, data and deployment settings.
6. It prevents hardware misallocation: an SBC (e.g. Raspberry Pi 5, Linux, watts of power) is overkill for simple control, while an MCU (e.g. Arduino Uno, 2 KB RAM) is too weak for heavy computing such as vision or databases.

Section E — Answers
Comparison
First concept
Second concept
1. Edge computing vs Cloud computing
Edge: processing near the data source; low latency, bandwidth savings, privacy; immediate decisions (reflexes).
Cloud: large-scale computing and storage over the Internet; long-term storage, analytics, AI training, dashboards; scales up/down; high availability (brain).
2. TCP vs UDP
TCP: connection-oriented, stateful; reliable in-order delivery; retransmits lost packets; flow and congestion control; used by HTTP, MQTT, WebSocket.
UDP: connectionless, stateless; no guaranteed delivery, ordering or duplicate elimination; low overhead for small, time-sensitive messages; used by CoAP.
3. Microprocessor vs Microcontroller
Microprocessor: processor IC needing external memory and I/O; heavier computation; e.g. Cortex-A76 in the Raspberry Pi 5.
Microcontroller: processor + memory + peripherals on one chip for a specific control function; e.g. ATmega328P, ESP32, STM32.
4. ASIC vs FPGA
ASIC: designed for one application; highest performance and optimisation; high development cost; inflexible after fabrication.
FPGA: programmable logic device; configurable logic and interconnections; reconfigurable; hardware acceleration and parallel processing.
5. Virtual machine vs Container
VM: own guest OS; heavier and slower to start; virtualised-hardware isolation; OS control, legacy workloads; Azure VMs, VM Scale Sets.
Container: shares the host kernel; lighter and faster; process-level isolation; portable packaging and repeatable releases; Container Apps, AKS, Container Instances.
6. Arduino Uno vs Raspberry Pi 5
Uno: MCU (8-bit AVR, 16 MHz, 2 KB SRAM); bare-metal; no native wireless; 6 analogue inputs; 5 V logic; ~0.22 W; high ease of learning.
Pi 5: SBC (quad-core 64-bit Cortex-A76 @ 2.4 GHz, 4–16 GB RAM); Linux; Wi-Fi, Bluetooth, Gigabit Ethernet; no ADC; 3.3 V logic; 2.7–12 W+; moderate to advanced.

FINAL EXAM CHEAT SHEET
IoT, edge and cloud (T1)
Body analogy: eyes/skin = sensors · nervous system = gateways · reflexes = edge · brain = cloud.
IoT = physical things + sensors + connectivity + data + action. Characteristics: interconnectivity · dynamic nature · scale · heterogeneity · self-adapting behaviour.
Four layers: sensors & actuators → gateways → cloud/server → applications.
Actuators: electric (precise) · hydraulic (heavy loads) · pneumatic (fast, compressed air). Gateway = device or software bridge that translates protocols and routes data.
Cloud = computing resources delivered over a network; rent not buy; scale up/down quickly; high availability; vertical (bigger) or horizontal (more).
Latency = delay to response. Bandwidth = max data rate (bps).
Edge = processing near the data source, not relying entirely on the cloud. Benefits: low latency · bandwidth savings (100 GB → 2 GB) · privacy. Edge ≠ automatically secure. Trifecta: IoT connects, edge responds, cloud scales.
Domains (T2)
Homes: smart lighting (LED, IP lights) · appliances (RFID fridge) · intrusion (PIR, door sensors, cameras; cloud location-aware; UPnP) · smoke/gas (optical, ionisation, air sampling; CO, LPG).
Cities: parking (slot sensors → local controller → cloud → apps) · road lighting · smart roads · structural health monitoring (vibration).
Environment: weather · air pollution (CO2, CO, NO, NO2; M2M) · noise (noise maps) · floods (ultrasonic level + flow velocity) · forest fire (temperature, humidity, light).
Retail: RFID inventory · NFC + Bluetooth payments. Logistics: fleet tracking (GPS) · shipment monitoring (temp, pressure, humidity). Agriculture: green house (sensors + valves/fan switches) · smart irrigation (moisture threshold). Health: wearables.
Architecture and protocols (T3)
Things = unique identity + remote sensing/actuating/monitoring. Interfaces: sensor I/O · Internet · memory/storage · audio/video.
Link: 802.3 Ethernet · 802.11 Wi-Fi (1 Mb/s–6.75 Gb/s) · 802.16 WiMAX · 802.15.4 LR-WPAN (40–250 kb/s; ZigBee) · 2G–4G (9.6 kb/s–100 Mb/s) · 5G NR (FR1/FR2; up to 20 Gbps; 1 ms; eMBB, URLLC, mMTC).
Network: IPv4 (32-bit, 2^32, exhausted 2011) · IPv6 (128-bit, 2^128 ≈ 3.4 × 10^38) · 6LoWPAN (IPv6 over 802.15.4; compression).
Transport: TCP (connection-oriented, stateful, reliable, flow + congestion control) · UDP (connectionless, stateless, no guarantees, low overhead).
Application: HTTP (request-response, TCP, stateless, port 80) · CoAP (request-response, UDP, constrained) · WebSocket (full duplex, TCP) · MQTT (publish-subscribe, broker, topics) · XMPP (XML, presence) · DDS, AMQP.
Functional blocks: device · communication · services · management · security · application.
Models: request-response (stateless) · publish-subscribe (broker, topics) · push-pull (queues, buffer) · exclusive pair (persistent, full duplex, stateful).
REST: client-server · stateless · cache-able · layered system · uniform interface. WebSocket API: HTTP upgrade handshake → persistent full duplex.
M2M = machine networking for monitoring/control; non-IP area network + IP communication network.
Embedded systems (T4)
Embedded = hardware + software inside a larger product for a specific function. Model: input → processing → output.
Components: MPU/MCU · memory (RAM, ROM, cache) · networking · I/O · storage (flash) · sensors; often an RTOS.
Cores: processors · ASIC (fast, costly, inflexible) · PLD (CPLD, FPGA — reconfigurable) · COTS.
MPU needs external memory/I/O. MCU = core + memory + peripherals on one chip (Cortex-M, STM32, ESP32, AVR, PIC, 8051). DSP = signal maths.
Interfaces: I²C (between ICs) · SPI (synchronous, fast; displays, flash, ADC/DAC) · UART (no shared clock) · 1-Wire · parallel. External: RS-232C, RS-485, USB, IEEE 1394; IrDA, Bluetooth, Wi-Fi, ZigBee, GPRS.
Classifications: event- vs time-triggered · soft vs hard real-time · small (8/16-bit) · medium (16/32-bit, DSP; GPOS/RTOS) · large (32/64-bit RISC, RSoC, multi-core, PLD, accelerators).
Azure (T5)
Terms: provisioning · subscription (access) · resource · resource group (container) · region (geography) · availability zone (separate location in a region) · IaC (versioned files) · telemetry · ARM (management layer).
Components: compute (VMs, Container Apps, AKS, Functions) · storage (Blob, Files, SQL) · networking (VNet, subnets, NSGs, Load Balancer) · identity/security (Entra ID, RBAC, managed identities, Key Vault) · monitoring (Azure Monitor, Log Analytics, App Insights).
Shared responsibility: IaaS → customer patches OS; PaaS → customer code, data, identities, config; serverless → code/images, permissions, data, settings.
Seven steps: requirements → design → organise → configure → provision → validate → operate.
Provisioning: portal (easy, drift) · CLI/PowerShell (scriptable) · ARM/Bicep (declarative, repeatable) · CI/CD (automated, secure secrets).
Scalability = handle more load. Elasticity = also scale down. VM = own OS; container = shares host kernel, lighter, faster.
Boards (T6)
MCU vs SBC first (avoid misallocation). Parameters: processing · connectivity · GPIO/interfaces · community/ease · power.
Uno R3: ATmega328P 8-bit, 16 MHz, 2 KB SRAM, 32 KB flash; 14 DIO (6 PWM), 6 analogue; 1 UART/SPI/I2C; 5 V; ~45 mA; no wireless.
Mega 2560: ATmega2560 8-bit, 16 MHz, 8 KB SRAM, 256 KB flash, 4 KB EEPROM; 54 DIO (15 PWM), 16 analogue; 4 UARTs; 5 V; ~70 mA.
Raspberry Pi 5: BCM2712 quad Cortex-A76 2.4 GHz; 4/8/16 GB; Wi-Fi ac, BT 5.0, Gigabit Ethernet; 40-pin 3.3 V; no ADC; 2.7–3 W idle, 8–12 W+ load; 5 V/5 A + fan.
ESP32: dual-core Xtensa LX6 240 MHz; 520 KB SRAM; Wi-Fi b/g/n + BT 4.2/BLE; ~34 GPIO 3.3 V not 5 V tolerant; 18 × 12-bit ADC, 2 DAC; deep sleep ~10–15 µA.
Blink bug: slide writes LOW to pin 12; use digitalWrite(6, LOW).

Common traps and exceptions
Edge does not replace the cloud and does not automatically make data private or secure.
The 19% lighting figure is for all lighting, not road lighting (slide error).
6LoWPAN is network layer; CoAP runs on UDP; MQTT is publish-subscribe; IPv6 is now RFC 8200; MQTT is officially just “MQTT”.
Real-time means meeting deadlines, not being fast. The Raspberry Pi 5 is an SBC, not an MCU. COTS, not “CoS”.
In IaaS the customer patches the OS. Scalable is not automatically elastic. Key Vault is identity and security, not storage.
Pi 5 has no ADC; ESP32 and Pi are 3.3 V; Uno/Mega have no native wireless; Uno R4 Minima is 32-bit. The slide’s blink code never turns the LED off.
